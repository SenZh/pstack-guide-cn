# Create a formal verification skill

测试检查的是有人想到要写的那些用例。形式化验证检查一个声明范围内的每个用例：模型里每一步排列、界内每个输入、或所有输入。本技能找出仓库里这件事最要紧的那部分，验证它的一个性质（property），并留下一个项目本地技能，让下一个 agent 能拿改动对照该性质来检查。写那个技能时，面向的是一个冷读它、正处于改动中途、从未见过你工作的 agent。用户必须能够信任结果并据以行动，而不需要先学那门验证语言。

## 从代码里选目标

从代码库回答，只有你无法观测的才问用户。用户点名了某个区域或某个 bug 的话，从那里开始。

好目标是一条代码作出的承诺，破坏它伤害用户，且测试很少触达破坏它的那个用例。在仓库里选最强的这类目标，不是最容易验证的那个。

## 让问题挑工具

挑以最低成本回答该问题的工具：模型检验器（model checker）、证明助手、SMT 后端的验证器，或别的工具。"事件能否以坏的顺序发生"通常适合对设计的小模型跑模型检验器，而 TLA+ 是任何语言下该用途的默认。"代码本身是否对每个输入都表现正确"，如内存安全、溢出、数据结构不变式，通常适合跑在代码上的验证器。这门语言没有验证器可跑的话，直说，并用生成的输入测试真实代码，不要测函数的手工模型。一个必须在任意规模下成立的性质，界不够用的时候，可能需要证明。优先选仓库的开发者装得上、跑得起来的工具，并向用户说明为什么选它。

## 什么算好

- **忠于代码。** 模型或证明的每一部分都指向审阅者能打开的代码。验证当作一个不可分步的东西，在代码里就是一个不可分步。命名来自本仓库。
- **能够失败。** 一个你从未见过失败的检查什么也证明不了。在它守护的代码的坏变体上展示每个性质失败，比如删掉一个检查、调换一步的顺序。
- **发现就是发现（findings stay findings）。** 当前代码破坏该性质时，用代码自己的语言连同反例（counterexample）一起报告。不要为了让它通过而削弱性质或模型，用户没要求就不改产品代码。
- **对范围诚实。** 说明验证了什么、在哪些界与假设之下、漏掉了什么。通过覆盖的是模型或界，不是整个系统。
- **不靠工具也能读。** 性质与危害各用一句平实的话陈述。反例用代码的语言按一串短步骤讲出来。
- **重跑便宜。** 一条命令、可复现的工具版本，运行短到下一个 agent 会在每个相关改动上都用它。
- **与代码保持同步。** 记录每个检查覆盖哪些文件与函数，以及你最后一次确认验证描述了它们的 commit。那次 commit 之后被覆盖代码变了，下一个 agent 能看出验证需要再看一眼。

## 生成验证技能

写一个项目本地技能，frontmatter 点名该区域并说明何时用它。没有 frontmatter，技能永远不会注册。仅凭这个技能，下一个 agent 必须能判断某个改动是否触到被验证的代码、跑检查、把真 bug 和建模错误区分开、并在改动是有意为之时更新验证。把覆盖记录和同步 commit 放进技能，并告诉下一个 agent：只有它确认验证描述了新 commit 下的代码，才把同步 commit 前移。用本仓库真实的命令、路径与名词，不留占位符。

如果检查是一个 TLA+ 模型，告诉下一个 agent 用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读每一个结果。它把检验器发现的每条不变式违反按最短路径用平实的话展示出来。检查通过时，`/statechart` 画出系统在状态间如何移动的图。用名字引用 `/statechart`。它的命令、选项和文件路径随版本与机器变化，所以不要把其中任何一个抄进生成的技能或其脚本。

## 交付前先证明

扮演下一个 agent，按生成的技能跑一遍：对一个破坏真实代码中该性质的临时改动（scratch change）执行。它必须抓住这个破坏。然后丢弃临时改动，确认检查回到原位：通过，或只在你将要报告的发现上失败。从未运行过的验证技能是草稿。技能漏掉破坏、或某一步跑不起来，就修技能或验证，不要修临时改动。

## 交接

告诉用户：你验证了什么、用了哪个工具、为什么、界在哪里、检查发现了什么（用平实的话）、怎么跑、它不覆盖什么。只有在你确实发现了一个相近目标时才建议第二个目标。指引用户去 `/maintain-formal-verification-skill`，在没有重新检查的改动之后把验证拉回与代码一致。
