# 修根因（Fix Root Causes）

> 翻译自 `skills/principle-fix-root-causes/SKILL.md`。本译文仅供人阅读，Agent 执行时读英文原文。术语见 [GLOSSARY.md](../GLOSSARY.md)。
>
> 技能名 `principle-fix-root-causes`（frontmatter 的 `name` 字段，寻址键，绝不汉化）。

---

**适用时机**：调试时。把每个症状回溯到系统最初出错的那一处并在那里修。守卫只有当它处理的状态合法时才算修复。

调试时修故障本身，不是它浮出的地方。症状是错误状态变得可见的位置。根因是系统第一次做不该做的事、或没处理该处理的状态的位置。

**为什么**：症状修复藏起证据，让故障自由地在别处浮出。每修一次症状，系统就更难推理，因为代码现在带着一个没人点过名的缺陷的变通。

**模式：**
- 先复现。
- 每一步问"为什么"，直到答案是代码里的一个错误决定，而不是更早决定的后果。
- 卡住就加仪表。读真实的错误与真实的状态。不要猜。
- 问触发症状的状态是否合法。系统可能合法处于该状态，那么在它上面坏掉的代码就是根因，在那里处理这个状态就是修复。该状态永远不该存在，那么在坏掉处加检查是把缺陷藏起来。找出制造该状态的东西。守卫、重试、吞掉的错误、被钳制的值、被丢弃的状态，是藏缺陷的常见方式。
- 某样东西只在重启后才失败，先怀疑持久化状态：配置文件、缓存、锁文件、序列化状态。
- 查模式，不只查实例。找到每个有同样故障的地方，全修。
- 一个变通需要一段落的注释来自证，代码就是错的。修代码，不是修注释。
- 若决定性的事实靠深挖才找到，提出那个第一眼就能显示它的、便宜的、常开的信号。
