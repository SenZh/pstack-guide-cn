# Maintain a formal verification skill

形式化检查证明的是它所描述之物的性质。
代码变了而验证没变，检查可能继续通过，但它描述的代码已不存在。
这种通过才是危险的情形，因为它看起来像一份证明。
本技能是 `/create-formal-verification-skill` 生成的验证技能的保养闭环，也适用于任何对指定代码跑模型检验器、证明器或代码级验证器的项目本地技能。
项目本地技能处理 agent 在使用它时顺手做出的改动。
本技能处理绕过它的改动：合并、没经过该技能的编辑、以及跨许多 commit 积累起来的漂移。

## 结果（Outcomes）

给每个检查一个结果，并说明是哪个：

- **in sync**：自上次同步以来没有任何变更改变检查所描述的内容，且检查通过。
- **updated**：代码变了，验证现在描述新代码，且检查通过。
- **bug**：验证描述的是当前代码，而代码破坏该性质。这是关于代码的发现（finding），不是漂移。
- **blocked**：检查无法拉回一致，或无法运行。精确说明原因。

一个检查可以既是 updated 又是 bug：更新让验证重新描述代码，然后性质在新代码上失败。

## 编辑范围（Edit scope）

只编辑验证本身：模型、宿主（harness）、性质文件，以及验证技能自身。
运行期间绝不编辑产品代码，除非用户要求你改。
性质在当前代码上失败时，不要为让它通过而削弱性质或模型。
报告失败。

## 巡检（Pass）

1. **找到检查。**
   验证技能没有固定名字，按它的行为找：一个对指定代码跑模型检验器、证明器或其他验证器的项目技能。
   逐个读你找到的，或用户点名的那个。
   对每个检查，收集：性质、它覆盖的代码、界与假设、运行它的命令、以及它最后一次被确认描述代码的 commit。
   没有验证技能存在，停下并指向 `/create-formal-verification-skill`。
   技能没记录同步 commit，就用最后一次改动验证文件的 commit，并说明你是这么做的。

2. **按现状跑一遍。**
   改任何东西之前，每个检查先跑一次并记录结果。
   这里的通过不告诉你代码是对的。
   它告诉你旧描述仍然成立。
   这里的失败可能是漂移也可能是 bug。
   到第 5 步之前不要裁决是哪个。

3. **通读被覆盖代码的每一个变更。**
   把被覆盖文件从同步 commit diff 到当前 commit，并读每条 commit message。
   同时留意移动过的代码：被覆盖的函数改名、拆分或挪到别的文件，它仍然是被覆盖代码。
   同时留意触到某个检查守护之状态的新代码，比如写同一批字段的新函数。
   对每个变更，判断它是下列哪种：
   - **无影响。** 变更不改变验证描述的任何东西，比如格式化、注释、验证不覆盖的代码路径。对照模型或宿主判断，不是对照 commit message。
   - **验证不再描述代码。** 原来一个不可分的动作现在变成两步、增删了一个分支、一个检查挪了位置、新路径到达被守护的状态、或某个值的范围变了。模型或宿主必须改。
   - **承诺有意变更。** 变更改变了代码的承诺，且变更中的证据表明这是有意的：文档注释、测试、changelog 或 commit message。性质必须改，且你必须引用那份证据。
   - **承诺可能被破坏。** 代码变了，且没有证据表明承诺变了。随之出现的失败按 bug 候选对待。

4. **按代码更新，不按结果更新。**
   改模型或宿主，让每个变更的部分重新指向审阅者能打开的代码，并保持代码里一个不可分步在验证里仍是一个步。
   先按代码写好更新再重跑，不要被"怎么让检查通过"塑形。
   只有承诺有意变更才改性质。
   写下旧表述、新表述和证据。
   保持界不变，除非变更使它们错了。
   必须缩小某个界的话，在报告里说明。

5. **重跑并裁决每个结果。**
   - **通过：** 检查如今可能在一个已经失去失败能力的描述上通过。按该性质防御的方式破坏新代码，比如删掉一个新检查、调换一步新顺序，确认检查抓住它。然后撤掉破坏。
   - **失败：** 把反例（counterexample）对真实代码逐步重放。某一步在代码里不可能发生，就是验证错了。修验证，并说明错在哪。每一步都可能发生，就是 bug。点名引入它的 commit，用代码自己的语言把反例按步骤序列讲出来，并用一句话说明危害。便宜的测试或对真实代码的复现能展示这个 bug 的话，把它作为证据加进报告。不要把它提交进产品代码。

6. **更新验证技能。**
   更新每个检查覆盖的代码、命令、界、假设和同步 commit。
   把同步 commit 设为你检查过的那个 commit。
   blocked 的检查不要前移同步 commit，并在报告里说明。
   然后扮演下一个 agent，把验证技能完整跑一遍，确认它的步骤仍然跑得通。

## 报告（Report）

对每个检查告诉用户：

- 结果，以及你读过的 commit；
- 验证里改了什么、为什么，每处变更一句简短理由：代码形状变了，或承诺有意变更（附证据）；
- 重跑结果，以及你用来展示更新后的检查仍能失败的那个破坏；
- 每个 bug，用平实的话：以代码语言按步骤表述的反例、危害、引入它的 commit；
- 验证仍不覆盖什么，包括它应当覆盖而未覆盖的新代码。

直说哪些失败是验证的漂移、哪些是代码的 bug。
更新前通过、更新后失败的检查，要说明旧的通过是建立在一个过时描述上的。

把验证更新放进一个独立的变更里，与任何产品修复分开。
