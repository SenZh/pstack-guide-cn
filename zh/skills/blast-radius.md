# Blast radius

在变更上线之前，找出它会在别处破坏什么。用于 "blast radius of X"、"what could this break"，或审查一个你还不信任的小 diff。

是 `how` 与 `why` 的伴生技能。`how` 告诉你代码做什么；`why` 告诉你它为什么长成这样；爆炸半径（blast radius）告诉你它会在别处破坏什么。

列出调用方不是这份工作。agent 一秒钟就能 grep 出来。这份工作是 grep 不会给你看的那些破坏。

## 别信你自己写出的报告（Don't trust your own writeup）

一份听起来头头是道的爆炸半径报告毫无价值。无论真假它读起来都令人信服。所以不要把报告交回去。找出整篇所依赖的那一两个事实，用运行代码来证明它们。

### 你有多大把握（How sure are you）

对变更的安全性所依赖的每个事实，尽量沿这条阶梯往下走，走到成本划算的深度，并说明它停在哪一级。

1. 你说了算。仅凭本身毫无价值。
2. 你指到了那一行。一个真实的 `file:line`，或库自己的源码。
3. 你论证了坏情形不会发生。你把失败过程一步步走了一遍，它走不到。
4. 你运行了它。一个脚本或测试，调用真实代码，你错了它就大声失败。
5. 你在运行中的应用里复现了它。

第 4 级通常就是一个小脚本：import 应用实际发布所带的同一个库，调用你担心的那个函数。

## 步骤（Steps）

1. 读变更。diff、它新增/修改/删除的符号、它现在行为上的不同，包括 diff 没有明说的部分。用 `why` 的 Step 2 拉 PR 与 commit。
2. 找出它之所以安全的那个唯一事实。大多数看似有风险的变更，都因一个单一事实而安全，比如"这次调用只会丢弃本已失效的缓存条目，此外什么都不做"。找到那个事实。它成立时，大多数风险情形一次性清空。把时间花在这里，而不是一张长长的"也许"清单上。
3. 看 grep 停在哪里。读你所调用库的源码，检查它锁定的（pinned）版本与任何本地补丁。理清事物何时运行：微任务、卸载与 teardown、Solid 与 React 的差异。追查符号搜索会漏掉的东西：一个 API 返回的 JSON、一个 DB 列、一种线上传输格式（wire format）、读同一批字节的另一种语言、一个 feature flag、下游三跳之外的代码。
4. 对每项风险保持诚实。给它一个真实的发生概率与真实的发生代价。确认过的风险保留；检查过并排除的单独列出。规则与 `why` 相同：引用真实的 `file:line`，一次一无所获的搜索同样是一个答案，绝不编造调用方或 API。
5. 证明那个唯一事实。写一个运行真实代码的脚本或测试，跑它，并把发生的事贴出来。
6. 大而广的变更，把它按 `arena` 跑。让不止一个模型回答同一个问题，合并答案。不同模型抓到的真实 bug 各不相同。

## 交回什么（What to hand back）

- **它做什么。** 改了什么，包括不明显的部分。
- **它之所以安全的那个唯一事实。** 陈述它，说明你把它推到了哪一级，出示证明。证明不了就写 unproven。
- **风险。** 每条写明它如何破坏、`file:line`、多可能、多严重，以及怎么核查。要紧的那几条贴出证明。
- **已排除（Cleared）。** 你检查过什么、为什么没问题。
- **合并之前（Before you merge）。** 能抓住真实 bug 的最便宜测试或复现（repro），包括你写的那个脚本。

通过 `unslop` 来写，引用真实代码，在它走向任何公开场合之前剥掉一切私密内容。

**回应：** 就是上面这份报告，那个唯一安全事实要么已证明、要么标注 unproven。
