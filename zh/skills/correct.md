# Correct

操作者在这个仓库不断为同样的错误纠正 agent。改仓库，让下一个 agent 犯不了。

假设每个贡献者都是一个 agent：只看它打开过的文件、抄最近的一个示例、走能编译的最短路径。把仓库设计成"从单个文件看是对的改动，对整个仓库也是对的"。

## 找出错误类别（mistake classes）

先读最近的 commit、revert、review 评论、agent 指令文件、以及解释变通方案（workaround）的注释。把错误归类。出现两次即算作一类。

## 在能生效的最高层级修每一类

1. **用架构消除它。** 每份状态一个属主，每类任务一条受支持的做法。把内部细节藏起来，让错误的 import 直接失败。用手写同步的列表换成一个唯一事实源。删掉旧做法和 agent 会去抄的死代码。
2. **用类型强制它，让坏状态写不出来。** 坏代码仍能编译的话，加一条 lint 或 CI 检查，其错误信息点名应改用的文件、类型或函数。模式已经很常见的话，只在变更新增更多时才失败。
3. **测试那个行为。** 修掉或删掉这类测试：它检查的行为坏了它还能通过；或只有内部变了它就失败。
4. **文档或 agent 规则最后写，只用于判断题。** agent 跳过它们时没有任何东西会失败。

## 修复并证明（Fix and prove）

现在就修最高频的类别，一类一个 commit。证明每个新检查在真实的既往错误上会失败。同一条命令本地与 CI 各跑一遍。例外写在违规行上，附理由、过期日期，并经一个人类批准。

## 维护规则表（rule table）

最后，在 agent 指令文件里维护一张表，把每条规则与强制它的机制配对。操作者纠正你时，修掉错误并把规则加上。规则本来就在却没有任何东西强制它，那就是重复犯错，于是在同一变更里按最高层级修掉它。某条规则的错误已经不可能发生，就删掉该规则。

**回应（Reply）：** 每个类别附其证据、你选的层级、以及更高的层级为什么不行。
