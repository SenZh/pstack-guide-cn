## Core 核心组

### 1. Laziness Protocol（懒惰协议）`principle-laziness-protocol`

**适用时机**：重构、评估 diff 尺寸、或想加抽象、分层、信号传递时。偏向删除与解决问题的最小变更。

- **合并决策。** 不要在多个地方重复同一个选择。把它放进唯一的事实来源，把结果作为简单 flag 传递。
- **最小化 diff。** 做能解决问题的最小变更。更少的行胜过"优雅"的样板。

---

### 2. Foundational Thinking（根基思考）`principle-foundational-thinking`

**适用时机**：写逻辑之前：选择核心类型与数据结构、排序脚手架与功能的先后、追问并发参与者共享什么。把数据结构做对，下游代码就会变得显然。

**结构性决策**保护期权价值。**代码级决策**保护简单性。

**数据结构先行。** 写逻辑之前把数据形状做对。尽早定义核心类型，追每一个访问模式，选与主导路径匹配的结构。

代码级上，对结构做 DRY，不是对每一行。类型与数据模型应当收敛。三句相似的话仍胜过一个过早的抽象。偏好显式而非聪明。测行为与边界，不测行数。

**并发推论。** 在参与者之间共享状态之前，问："另一个参与者并发修改它会怎样？"若答案不是"什么都不会"，就隔离。

**脚手架先行。** 若某样东西帮到之后每个阶段，先做它。问"之后每个阶段都因它存在而受益吗？"CI、lint、测试基础设施、共享类型是脚手架。为期权价值排序：setup 在功能之前，测试在修复之前。commit 保持小而单一目的。

每个增量应落地一个连贯的抽象，或加深一个已有的抽象。不要把新能力以特例协调的方式摊到各调用方。

减法先于脚手架。先删死代码，再打地基。

---

### 3. Redesign from First Principles（第一性重设计）`principle-redesign-from-first-principles`

**适用时机**：把一个新需求接进已有设计时。

接入变更时，不要把它拴在现有设计上。假想这个需求从第一天起就是根基假设，照此重设计。

- 读所有受影响文件，理解当前设计
- 问："如果我们带着这个新需求从零写，我们会建什么？"
- 把变更传播到每一处引用：类型、文档、示例、rationale 段落
- 想清楚整个重设计，然后增量交付

这是把变更接进已有设计时保住期权价值的方法。

---

### 4. Attack the Premise（攻击前提）`principle-attack-the-premise`

**适用时机**：两个以上共享同一前提的修复在同一关卡失败。把前提写下来并直接检验，再写下一个假设它的修复。

当两个以上共享同一前提的修复在同一关卡失败，怀疑的是前提，不是修复。

**为什么**：每个失败的修复都是对它所假设信念的反证。在同一前提上的第三个修复，把努力花在证据已经说"原因不在这里"的地方。

**模式：**
- **把前提写下来。** 前提是每个失败修复都假设的那一句话。
- **下一次修复之前先检验前提。** 找一个"若前提为假则结果不同"的观测，把它做出来。看失败的分布方式，不只看失败的大小。让检查可重跑，按 [Build the Lever](./principles.md)。
- **跟着证据走。** 它与前提矛盾，原因就在别处。找失败之间前提没能预测的共同点。它确认前提，就按 [Fix Root Causes](./principles.md) 问下一个"为什么"。更早的修复可能治的是后果而不是原因。
- **移除条件，而不是补偿它**，按 [Laziness Protocol](./principles.md)。若证据显示某一部分总是落在输的一边，改变把它放到那里的东西。一个在事后清理的机制让原因原地不动，还给每次运行加活。

**停止条件**：前提写下来并检验之前，不开始下一个修复。

本原则区别于 [Redesign from First Principles](./principles.md)：后者围绕新需求重建设计；本条质疑当前设计所假设的一个事实。

### 5. Subtract Before You Add（先减后加）`principle-subtract-before-you-add`

**适用时机**：排序一个新增、重构或重写时。先移除死代码、冗余校验器、stub 引用，再在更简单的基座上构建。

演化系统时，先移除复杂度，再构建。默认做减法。

把简化当作持续投资。留下比你发现时略更简单、且在同一或更小表面之后更有能力的设计。

- 移除先于构建排序
- 打磨之前先砍（先到达最小，再投资质量）
- 为观测到的用法设计，不为推测的边界情况
- 不放规格要求之外的推测性校验器、解析器、守卫
- 简化提示词（删冗余指令、过度模板）
- 引用没有新内容时，删掉它而不是留一个 stub

---

### 6. Minimize Reader Load（最小化读者负荷）`principle-minimize-reader-load`

**适用时机**：审阅或塑形难以追踪的代码。数清问题与答案之间的层数、读者脑中的隐藏状态；收掉单调用方包装，缩小可变作用域。

可维护性是读者理解代码必须做的工作。追踪两个轴：**要追的层**（问题与答案之间的间接层）与**要持有的状态**（读者必须记在脑中的隐藏或可变上下文）。LOC、圈复杂度、"clean architecture"都是代理指标。读者负荷才是要紧的东西。两个轴相互独立：一个 50 个全局变量的扁平文件，可以和 6 层适配器栈一样难推理。两个都守。这是 [Guard the Context Window](./principles.md) 的人类版本——读者的工作记忆同样是有限的。

- **收掉省不过本的层**：只有一个调用方的包装、没有第二个实现的适配器、从未被需要的投机间接层。内联它们。
- **相邻层必须改变抽象。** 重复同样方法与参数的层只加负荷不加压缩。收掉直通层。
- **要求接口压缩。** 藏不住多少复杂度的宽接口让读者既学表面又学实现。优先能藏住有意义决策的边界。
- **缩小状态作用域**：纯函数（返回而非变更）优于局部变量，局部变量优于字段，字段优于模块状态，模块状态优于全局。派生优于同步。
- **在边界点名不变式**，而不是在每个消费方，让读者只学一次。
- 加一层或一份数据状态之前问：它在别处减少的读者负荷至少与它增加的相当吗？

**检验**：一个新读者能在 30 秒内回答"X 从哪来？"和"什么能改 X？"吗？不能，就砍层或砍状态。

---

### 7. Outcome-Oriented Execution（结果导向执行）`principle-outcome-oriented-execution`

**适用时机**：有明确阶段边界的计划性重写与迁移。向目标架构收敛；不用一次性兼容代码保住平滑的中间态。

优化预期的、可验证的终态，而不是保住平滑的中间态。

**为什么**：让每个中间步骤都完全稳定，常会制造变成永久债务的临时兼容代码。向目标架构收敛，在显式验证边界证明正确性。

**核心规则：**
- 终态完整性优先于过渡期稳定性
- 计划内、有范围、可回退的中间破坏是可接受的

**护栏：**
- 只用于有明确阶段边界的计划性重写与迁移
- 声明哪里允许临时破坏
- 迁移期间对活跃触及区域保持高信号检查
- 计划完成时要求完整的静态与运行时验证

---

### 8. Experience First（体验优先）`principle-experience-first`

**适用时机**：产品、UX 或功能范围的权衡出现时。选用户惊喜，不选实现便利；交付更少但打磨好的功能，而不是更多粗糙的。

实现便利与用户惊喜冲突时，选惊喜。

- 每个功能、控件、选项都必须有存在的理由
- 少交付，交付好（三个打磨好的功能胜过十个粗糙的）
- 先原型再定夺（设计决策在一次性 HTML 里比在生产代码里便宜）
- 把细节做对（过渡、对齐、间距、反馈、错误态）
- 收紧核心循环（每个功能要么服务中央工作流，要么让路）

用户是消费这件工作的人。UI 的用户是终端用户；库或内部 API 的用户是 import 它的同事；下一位维护代码的工程师也是用户。同等权衡他们的体验，并从他们的视角解释影响。

地基为体验服务。根基思考（foundational thinking）管工作的**顺序**；本原则管**目标**。

---

### 9. Exhaust the Design Space（穷尽设计空间）`principle-exhaust-the-design-space`

**适用时机**：面对代码库中无先例的新 UI 交互或架构决策。造 2-3 个竞争原型，并排比较之后再定。

它同样适用于体验取决于感觉而非逻辑的产品设计决策。

---

### 10. Build the Lever（造杠杆）`principle-build-the-lever`

**适用时机**：任何非平凡工作，不只批量工作：编辑、迁移、分析、检查。造那个能做它或能证明它的工具（codemod、脚本、生成器、或你的子智能体遵循的技能），而不是手工做。这个工具就是审阅者能重跑的制品。

工作不平凡时，造那个能做它的工具，而不是手工做。

codemod、生成器或脚本每次以同样方式做这份工作，且重跑免费。这个工具是审阅者可以读并重跑来核对工作的一个制品。手工变更只能靠重做来复验。确定性脚本把"信我"变成"跑这个"。

默认造杠杆。只有任务是平凡的——几处一眼就能看完的显然编辑——才跳过。

- 先手工做第一个单元来学会配方，然后造工具。在那一个单元上重跑工具、diff 你手工的版本来证明它。让杠杆可以安全重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用灌进 sqlite 的查询，验证用可重跑的检查。
- 确定性杠杆胜过 fan-out。工具能一遍处理所有单元就自己跑。不要派一堆委派者去手工应用一个脚本能做的事。
- 把工作派给子智能体时，把杠杆写成它们都读的技能：配方、验证契约、不可触碰的围栏，一个制品。放在委派者的写权限之外，让它们没法悄悄改契约。
- 应用本原则会产出一个文件。若你引用了它而 diff 里没有 codemod、脚本、生成器或委派技能，你就是没应用它。
- 工作活得比会话长时，把杠杆提交入库。

门槛是平凡性，不是重复性。当杠杆正是让工作可检查的东西时，一次性工作也值得一个杠杆。按 [Laziness Protocol](./principles.md)，造能做或证明这件事的最小脚本，绝不是一个框架。

区别于 [Encode Lessons in Structure](./principles.md)（把反复出现的指令变成持久护栏）。本条是面前工作的吞吐量与可评审性。把验证本身脚本化见 [Prove It Works](./principles.md)。

## Architecture 架构组

### 11. Model the Domain（为领域建模）`principle-model-the-domain`

**适用时机**：写有状态逻辑，或代码分支很多、或在多文件间重复同一形状假设时。

把真实领域编码进一个数据结构，而不是散落在条件判断里。匹配领域的结构让非法状态不可表示，并删掉分支。写代码时选它很便宜；之后再恢复它看起来像一次重构，于是被无限推迟。

够向：

- 用状态机，不用散落的布尔量、阶段、生命周期检查。
- 用带类型的模型，不用松散参数或重复的形状假设。
- 用 map、注册表、查找表、可判别联合，不用散落多文件的分支。
- 用 reducer 或命令/事件模型，不用临时的状态变更。
- 用围绕一份领域知识组织的模块，不用"加载、校验、转换、保存"这样的顺序。执行顺序不是所有权。
- 用一个小的模块边界收拢重复的行为、所有权或不变式。
- 访问模式需要时，用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。都不合适时，弄清代码绝不允许什么、数据怎么被读，然后找到恰好编码这两件事的结构。

不硬造抽象。当前形状已经清晰、局部、不太会长时，无聊的代码就留着。对"加了间接层却没删掉分支、重复规则、非法状态或生命周期风险"的抽象保持怀疑。

跳过本条的标志：一个新功能让已有的 if/else 链长出一个分支，或第二个必须与第一个保持同步的布尔量。按时间分解是另一个标志：以阶段命名的模块在多个步骤里重复同样的领域规则。

### 12. Boundary Discipline（边界纪律）`principle-boundary-discipline`

**适用时机**：接校验、错误处理或框架适配器时。把守卫集中在系统边界（CLI、配置、网络、外部 API）；信任内部类型，业务逻辑放进纯函数。

把校验、类型收窄、错误处理放在系统边界。无条件信任内部代码。业务逻辑活在纯函数里。壳是薄的、机械的。

**为什么**：散落的校验吵、冗余、给人虚假的安全感。把逻辑拿出框架接线，它才能脱离框架被测试。

**模式：**
- **在边界**（CLI 参数、配置文件、外部 API、网络协议）：校验、返回错误、防御性处理。
- **系统内部**：带类型的数据、错误传播、不再校验。信任类型。
- **跨越边界。** 暴露领域概念，不暴露边界的私有表示。通用机制留在内部，专用策略放在边缘。

**应用：**

校验与错误处理：
- 在解析时（边界）校验配置，不在业务逻辑里
- 在边界把原始数据解析成领域类型
- 不把传输、存储、框架、线上格式类型从公开表面再导出
- 边界已校验的前提下，调用链深处不做冗余判空

代码组织：
- 业务逻辑放进无框架依赖的纯函数
- 解析函数：从原始字节到带类型状态的纯转换
- 提示词构造：结构化状态进，字符串出
- 评分与评估：从状态到结果的纯转换

**检验：**
- "这份数据此刻正在跨越系统边界吗？"不是，校验就是冗余。
- "它能成为一个壳只管调用的纯函数吗？"能，就抽出来。

### 13. Type System Discipline（类型系统纪律）`principle-type-system-discipline`

**适用时机**：设计类型、审查函数签名、或在任何静态类型语言里写代码。让非法状态不可表示，给语义原始类型打品牌，在边界解析外部数据，穷尽变体，从权威 schema 派生。

让编译器拒绝不可能的状态、错配的原始类型、未处理的变体。优先把错误与特例定义到"不存在"，而不是增殖处理器。TypeScript 语法见 `typescript-best-practices` 技能。

- **给语义原始类型打品牌。** `UserId` 与 `OrderId` 底层都是字符串，但不该可互换。各自给一个类型，如 TypeScript 的品牌交叉类型或其他语言里的 newtype。创建时验证一次，下游信任类型。两个参数共享原始类型却含义不同时，打品牌。
- **外部数据在解析前无类型。** RPC 载荷、JSON、IPC 消息、CLI 参数、配置文件、环境变量、数据库行。每个边界一个解析函数，把非结构化输入变成带类型的模型。**boundary-discipline** 原则技能说校验放哪。
- **从权威 schema 派生类型。** 协议缓冲、OpenAPI spec、GraphQL schema、数据库迁移、design-token 文件或另一个文件拥有某个形状时，从它派生，不手搓平行类型。见 **encode-lessons-in-structure** 原则技能。

### 14. Make Operations Idempotent（让操作幂等）`principle-make-operations-idempotent`

**适用时机**：设计在崩溃、重启、重试中运行的命令、生命周期步骤或处理循环。无论之前跑过多少次、停在哪，都收敛到同一个终态。

设计操作，让它无论跑多少次、上次停在哪，都收敛到正确状态。每个变更状态的操作都要回答："跑两次会怎样？上次跑到一半崩了会怎样？"

**为什么**：命令、生命周期操作、处理循环运行在崩溃、重启、重试是常态的环境。若部分状态会改变下一次运行的结果，每次重启都变成一场调试。

**核心想法**：每一步从存在的状态派生，而不是从上一次运行"想做"的事派生。读当前状态，与目标比较，只应用差异。这样写的步骤可以安全重复，因为重复会发现无事可做。

一次运行留下的任何东西——锁、临时文件、半写的记录、被认领的任务——都必须能被下一次运行识别为过期。过期与否的判据，要在"上次运行可能停在的任何位置"都成立，而不是只在常见情形成立。下一次运行无法判定的标记，把每次崩溃都变成手工清理。例如：写到临时路径再 rename 到位，或按内容而不是创建顺序比较制品。

**检验：**
1. 连跑两次会怎样？
2. 上次在每个可能的点崩溃会怎样？
3. 重复执行会收敛到同一个终态吗？

任一答案是"取决于留下了什么状态"，这个操作就需要一个对账步骤。

---

### 15. Migrate Callers Then Delete Legacy APIs（先迁移调用方再删旧 API）`principle-migrate-callers-then-delete-legacy-apis`

**适用时机**：引入新内部 API 而旧调用方仍存在时。同一波之内迁移调用方并删除旧 API，而不是保留兼容层。

- 更新测试以断言新契约，删除只保护重构前实现细节的测试

**适用条件：**
- 没有外部用户依赖向后兼容
- 项目能吸收协调好的破坏性变更
- 新 API 是某次简化或重构行动的一部分

---

### 16. Separate Before Serializing Shared State（先分离再串行化共享状态）`principle-separate-before-serializing-shared-state`

**适用时机**：并发参与者可能写同一文件、分支、键或状态对象时。先消除共享；只有一个共享写入者是真实不变式时才做结构化串行化。

并发参与者可能共享可变状态时，先问它们是否需要同一个可变对象。不需要，就消除共享。共享是真实的，就在结构上强制串行化：锁文件、顺序阶段、独占所有权。指令与约定不是并发控制。

**为什么**：对共享状态的并发写入制造间歇、难复现、调试昂贵的竞态。

**模式：**
1. **识别共享可变状态**（双方读写的文件、双方 push 的分支、双方定义并消费的 API）。
2. **默认：消除共享写目标。** 问：这些参与者需要一个规范对象，还是各自发布独立的事实？给每个参与者自己的文件、键、分支或状态目录，只在读/报告边界合并。两个 worker 把各自的 `lastX` 字段写进同一个 `state.json` 仍是共享变更。`indexer-state.json` 加 `metrics-state.json` 就不是。
3. **只有一个共享写目标是真实不变式时，才在结构上串行化访问**（锁文件、顺序阶段、单写入者 actor、或原子 compare-and-swap）。把"我们需要一把锁"当作要核查的设计坏味道，而不是默认答案。

---

## Verification 验证组

### 17. Prove It Works（证明它真的能跑）`principle-prove-it-works`

**适用时机**：完成一个任务之后、宣布完成之前。对着真实制品验证（运行该功能、读真实值、检查 diff），不用代理指标、自报、"能编译"。

通过直接检查真实的东西来验证每个任务输出。不从代理、自报、"能编译"推断。

**为什么**：未验证的工作正确性未知。间接验证（文件 mtime、输出新鲜度、agent 自报、缓存的截图）感觉比直接观测便宜。基于错误推断行动的代价远高于查源头。

查真实的东西，不查代理：
- 直接查进程活性，不通过派生态间接查
- 读真实值，不读缓存或派生的表示
- 验证失败时，先怀疑观测方法，再怀疑系统

## 能脚本化就脚本化检查

最强的证明是一个确定性脚本重跑同一次比较，不是一次性肉眼。写脚本、跑它、把输出留作审阅者可重跑的制品，而不是信你一句话。

让制品对人可见。只有大或复杂、轨迹日后要可审计的工作才提交入库，如一次大移植或迁移（**show-me-your-work** 技能）。

---

### 18. Fix Root Causes（修根因）`principle-fix-root-causes`

**适用时机**：调试时。把每个症状回溯到系统最初出错的那一处并在那里修。守卫只有当它处理的状态合法时才算修复。

调试时修故障本身，不是它浮出的地方。症状是错误状态变得可见的位置。根因是系统第一次做不该做的事、或没处理该处理的状态的位置。

**为什么**：症状修复藏起证据，让故障自由地在别处浮出。每修一次症状，系统就更难推理，因为代码现在带着一个没人点过名的缺陷的变通。

**模式：**
- 先复现。
- 每一步问"为什么"，直到答案是代码里的一个错误决定，而不是更早决定的后果。
- 卡住就加仪表。读真实的错误与真实的状态。不要猜。
- 问触发症状的状态是否合法。系统可能合法处于该状态，那么在它上面坏掉的代码就是根因，在那里处理这个状态就是修复。该状态永远不该存在，那么在坏掉处加检查是把缺陷藏起来。找出制造该状态的东西。守卫、重试、吞掉的错误、被钳制的值、被丢弃的状态，是藏缺陷的常见方式。
- 某样东西只在重启后才失败，先怀疑持久化状态：配置文件、缓存、锁文件、序列化状态。
- 查模式，不只查实例。找到每个有同样故障的地方，全修。
- 一个变通需要一段落的注释来自证，代码就是错的。修代码，不是修注释。
- 若决定性的事实靠深挖才找到，提出那个第一眼就能显示它的、便宜的、常开的信号。

---

### 19. Sequence Work into Verifiable Units（串成可验证单元）`principle-sequence-verifiable-units`

**适用时机**：多步骤工作（清扫、迁移、成串同类编辑）及 commit 与 PR 的堆叠方式。把工作拆成每步以可检查状态收尾的小单元，逐个检查再进下一个，排序交付让序列向审阅者自我证明。

把工作排成小单元的序列，每个单元以一个你能检查的状态收尾，当前单元不绿就不前进。

**为什么**：在肇事的单元被抓住的破坏，定位很便宜。批次之后才被抓住的破坏已被埋住，而你已经在坏基座上继续建了。把这些单元排成审阅者可重放的交付，把"信我"变成"看它先红后绿"。

**执行。** 清扫、迁移或任何成串同类编辑里，先验证每个变更再开始下一个。每个单元是一个前后括号：已知好状态、一个变更、跑检查、再前进。先 rebase 到干净 trunk，让每次检查都对真实基线。有杠杆做编辑时，逐单元检查几乎免费。也要跑。

**交付。** 按能证明工作的顺序堆叠 commit 与 PR。标准形态是失败测试在下、修复在上。其他叙事顺序：重塑之前先减法、处理之前先采基线、功能之前先脚手架。每个 commit 独立可落地，序列读起来像一段论证。

它是 **prove-it-works** 原则技能（让每次检查为真）与 **build-the-lever** 原则技能（让逐单元检查便宜）的排序互补。

---

### 20. Test Behavior, Not Implementation（测行为不测实现）`principle-test-behavior-not-implementation`

**适用时机**：写、改、保留一个测试时。断言代码使用者能观测到的东西，让行为坏时测试失败、仅内部变化时测试保持通过。

测试是对"代码为其使用者做什么"的主张：一个调用方、一个终端用户、或另一个服务。行为是这些使用者通过他们使用的接口能观测到的东西：返回值、错误、能读回的状态、对代码之外系统的影响——一个发出的请求、一行写入、一条消息。实现是他们观测不到的：私有助手、内部调用顺序、中间数据、哪个内部协作者干了活。

用两个假想编辑审判每个测试：

- **破坏行为。** 让代码返回错误值、跳过一个效果、或把效果做两遍。测试仍通过，它就什么都没证明。常见原因：断言松于契约、期望值由被测代码计算、复述从不运行读取它的代码的常量或提示词字符串、对测试自己构造的数据做断言。
- **改内部。** 保持所有可观测结果不变，重构底下的代码。测试现在失败，它就钉死在实现上。每次重构都要重写，却仍抓不到缺陷。

保留能抓住第一个编辑、并活过第二个编辑的测试。重写或删除其余。写出两者兼备的测试：通过使用者的接口以具体输入驱动代码。期望值从需求派生，不从代码的一次运行派生。断言契约承诺的东西，不多不少。

契约说了算，不是断言的形状。"空购物车永不扣款"是承诺时，"支付客户端没被调用"的断言就是行为。配一个确实扣款的用例，让测试证明它看得见调用。被 mock 的外部服务收到的载荷是行为，因为那个服务观测它。对内部助手的调用是实现，因为没有使用者看得见。空列表在"无记录匹配"时是精确答案，在"测试只需要随便一个结果"时是空壳检查。精确的错误信息钉死了没有调用方读的措辞。调用方据以分支的错误类型才是契约。

测试可以钉一个不变式而不是一次调用，如一个键必须存在于两张表、或一个编译期类型检查。不变式就是行为。

### 21. Explain the Number（解释那个数字）`principle-explain-the-number`

**适用时机**：测量之前，以及信任、汇报、据以行动某个你测出的数字之前：加速、回退、吞吐、延迟、eval 结果。找出限制它的是什么，并排除它测量的其实不是你以为的那件事。

- **跑之前写下决策。** 点名什么结果会改变决策，以及噪声地板。run-to-run 波动大于效应时就停。
- **问"为什么不是两倍？"** 点名限制结果的资源或代码路径：一个核、一把锁、磁盘、网络、或压测器本身。从 profile 或运行期间的系统计数器拿它，再映射到源码。读代码得出的猜测不是限制器。说不出数字为什么没好两倍，你就不知道自己测了什么。
- **列出这个数字还可能在测什么，逐个用证据排除。** 常见嫌疑：错误、被跳过或缓存的工作、从未运行的代码、未调优的一侧（留在默认设置）、噪声、以及端到端太小不足道的一段。
- **证据与数字放在一起。** run 数、波动、限制器，写进笔记或链接的制品。

性能数字按 [benchmark-checklist](./benchmark-checklist.md) 技能跑完整流程。eval 结果对试次问同样的问题：每次 run 都做了任务吗、差距跨试次与模型都成立吗、场景重要吗。

你跳过了本条，当：run 开始时没写下会改变决策的结果；数字背后的证据没有 run 数、没有波动、没有点名的限制器；或省下的时间大于被改那一段原本花的时间。

区别于 [Prove It Works](./principles.md)（检查输出是真的）。

## Delegation 委派组

### 22. Guard the Context Window（守住上下文窗口）`principle-guard-the-context-window`

**适用时机**：上下文被填满时：大输出、长文件、重复读、fan-out 规划。把重活路由给子智能体；主线程留摘要，不留原始载荷。

**为什么**：上下文溢出劣化推理质量，制造压缩伪影，让进展停摆。

**模式：**
- **给阶段定尺寸并封顶范围。** 限制每阶段文件数、设回合预算、计入机制成本。

---

### 23. Never Block on the Human（绝不停下来等人类）`principle-never-block-on-the-human`

**适用时机**：对可逆工作想说"要不要我做 X？"时。

人类异步监督。agent 必须保持不被阻塞。做合理的决定，继续，让人类事后纠偏。代码变更可逆且可评审，一个错误决定通常比阻塞便宜。

- 先做，再呈现。完成工作，展示结果。不问"要不要我做 X？"。做 X，解释为什么。
- 让系统自愈。发现问题就记下来，下一轮修。
- 不可逆动作（强推、删生产数据、发外部消息）仍需确认。
- 可逆动作（写代码、编辑笔记、拆任务）不应被阻塞。
- 产品方向来自人类。执行不应被阻塞。

---

## Meta 元

### 24. Encode Lessons in Structure（把教训编码进结构）`principle-encode-lessons-in-structure`

**适用时机**：你发现自己第二次写同一条指令，或注意到一个反复出现的纠正时。把规则编码成 lint、元数据 flag、运行时检查或脚本，而不是更多的文字。

若教训需要判断、无法被编码，就把指令做得更醒目，并附一个该失败模式的示例。

**推论**：修复是结构性的，就只用结构修复。指令只是症状。
