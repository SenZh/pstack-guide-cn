# Maintain a verification skill

应用一变，功能地图就开始腐烂。本技能是 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的保养闭环。严谨的单位是功能，不是每句话：从源码覆盖每个功能文件、活体演练每个功能，而不把每条要点都推到终局验证。

## 结果（Outcomes）

选一个，并说明是哪个：

- **clean** — 每个功能都得到了源码与活体覆盖；没有值得交付的改动。不开分支，不开 PR。
- **changed** — 一个 PR 交付经过证明的文档、宿主或地图修正。
- **blocked** — 覆盖没能完成，或经过证明的修复无法安全交付。精确说明阻塞它的是什么。

## 编辑范围（Edit scope）

只编辑验证技能自己的目录（它的 SKILL.md、features/、以及它拥有的任何宿主脚本）。运行期间绝不编辑产品代码：地图描述的某个行为应用已经不做了，要么是文档漂移（修地图），要么是产品回归（报告它，不要用文档掩盖它）。

## 巡检（Pass）

0. **定位目标。** 找到要维护的验证技能：项目本地技能，正文里有 launch/drive 小节和一个功能地图（通常是项目技能目录里的 `verify-*/`：`.cursor/skills/`、`.claude/skills/`、`.pi/skills/` 或 `.agents/skills/`）。多个候选 → 问是哪个；一个都没有 → 停下并指向 `/create-verification-skill`，不要凭空捏造目标。

1. **索引卫生。** 读功能地图 README，glob 它的同级文件。修掉缺失、多余、重复、失效的条目。轻量；不生成清单。

2. **源码波次。** 每个功能文件一个只读子智能体，并发启动。每个从源码解释"这个用户可见功能是怎么工作的？"，带引用标记可能的文档漂移，并返回一份简明的活体验证配方。子智能体从不驱动应用、从不编辑文件。返回形状：功能摘要 / 源码入口 / 可能的漂移或无 / 一份配方。

3. **对账。** 每个功能文件都有一份返回的摘要。把重叠的配方合并成实际可行的最少应用状态。抽查有引用的漂移；不重新证明干净的论断。扫一遍近期的代码变动，找地图缺失的用户可见交互面——点名某个缺失之前要求具体的源码路径。

4. **活体巡检。** 源码看起来干净也必须做。协调者拥有全部驱动；遵循验证技能自己的 launch 模型——服务器与 UI 用一个长活实例串行驱动，短命 CLI 每次驱动用全新隔离会话（由该技能的 Launch 小节决定，不是本技能）。每个功能至少演练一次，且无论出现什么失败，整个巡检期间守住三条不变式：(1) 绝不驱动一个自上次做出意外行为后没体检过的实例——首次驱动前 doctor，以会话为单位时每个新会话 doctor，任何失败的驱动之后再 doctor，doctor 看不见失败的地方（健康进程上卡死的 UI 状态），重置到已知状态或重启，不要心存侥幸；(2) 到当前为止捕获的证据在每次清理后幸存，在指定位置核实，不是假定；(3) 驱动启动的任何东西不比那次驱动的有用期活得久——失败迭代的残留无论会话卡死、退出还是共享都要清理（共享实例清残留，不清实例）。技能漂移导致的 doctor 失败就是漂移：在编辑范围内修好并重试一次——重启该修复使之失效的东西，仅此而已——之后才把巡检标为 `blocked`。无法到达的功能只有拿到具体前置条件（认证、权益、OS、外部状态）与尝试过的路径才能标 `verified-unreachable`；地图漏了那个前置条件，那就是漂移。分诊产生的任何宿主修复，交付前要重新活体驱动。最终拆除发生在本次运行的最后一次驱动之后——包括那些重新证明——所以没有任何东西比运行活得久（证据留下，按该技能的规定）。

5. **分诊。** 错误或缺失的用户视角描述 → 文档漂移，修它。宿主驱不动的正常行为 → 宿主缺口，修它；宿主修复遵循与生成相同的 helpers 规则（脚本可执行、调用方式写在技能正文）。实际坏掉的应用行为 → 产品缺口；为用户记录它，挡在本 PR 之外。

6. **交付或停止。** changed：一个 PR 装经过证明的修正，先重读每个改动的文件。clean 或 blocked：不开 PR，诚实报告结果与覆盖情况。

把简明的运行笔记（覆盖的功能、不可达的前置条件、确认的漂移、结果）放在临时位置；不提交它们。
